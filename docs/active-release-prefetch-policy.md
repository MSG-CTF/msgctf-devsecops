# 운영 버전 기준 이미지 사전 다운로드

## 2026-10-27 운영 결정

최초 준비 대상은 **현재 운영 버전(active release)의 전체 컨테이너**입니다.
문제가 수정되면 검사·발행·등록한 새 버전의 전체 컨테이너를 추가로 준비합니다.
최신 발행본이라는 이유만으로 현재 운영 버전을 바꾸지 않습니다.

| 상황 | 사전 다운로드 대상 | 기존 버전 처리 |
|---|---|---|
| 최초 준비 | Backend가 확정한 문제별 active release의 전체 컨테이너 digest | 현재 active와 실행 중 인스턴스 유지 |
| 새 버전 등록 | 적용할 새 release의 전체 컨테이너 digest | 등록·준비만으로 active 변경하지 않음 |
| 새 버전 적용 | 승인된 대상 노드에서 준비를 확인한 새 release | 기존 참가자 인스턴스는 기존 release 유지 |
| 준비 실패·용량 부족 | 실패 원인과 노드별 결과를 표시하고 명시적으로 재시도 | 이번 자동 전환은 진행하지 않고 기존 운영 버전 유지 |
| 노드 추가·교체 | 해당 노드에 승인된 현재 운영 release와 적용 대기 release | 관측 전에는 준비 완료로 표시하지 않음 |

공개 컨테이너뿐 아니라 DB 등 비공개 보조 컨테이너도 포함합니다. `latest`나
tag를 노드에서 해석하지 않고, 해당 release에 저장된 GHCR digest를 그대로 사용합니다.
KOTH·Windows·정적 문제와 과거 전체 revision은 이번 일괄 준비 대상이 아닙니다.
별도로 승인한 롤백 버전을 추가 준비할 수 있지만, 과거 전체 이력을 받지는 않습니다.

## 최신 발행 목록과 운영 목록의 차이

`collect_node_image_plans.py`는 공식 main의 문제 소스와 일치하는 성공 발행본을
취합하는 **출처 대조 도구**입니다. Backend DB의 active release를 조회하지 않습니다.
따라서 이 도구가 만든 최신 목록을 그대로 현재 운영 버전 목록이라고 부르거나
일괄 활성화하지 않습니다. 기존 목록 형식이나 CI에 Backend 토큰을 추가하지 않습니다.

운영 대상 선택의 기준은 Backend의 실제 active release입니다. Backend는 자신의
release ID·revision과 원본 `artifact-v2.json`의 전체 컨테이너·architecture·실행
사양을 연결하고, Runtime이 허용한 target·용량 범위로 준비 요청을 구성합니다.
선택 범위와 기준 시각을 확인할 수 없으면 일괄 다운로드를 시작하지 않습니다.

보조 `plan.json`은 name·image 목록과 출처 대조에만 사용합니다. Runtime 요청이나
실제 현재 준비 상태, 실행 승인, Backend active 선택을 대신하지 않습니다.

## 업데이트와 적용 흐름

```text
문제 변경 -> main 검증·발행 -> GHCR digest + publish bundle
  -> Backend가 새 release 등록 (기존 active 유지)
  -> 승인된 새 release의 모든 컨테이너 준비 요청
  -> Runtime이 대상 노드의 실행 CRI에서 다운로드·현재 상태 관측
  -> 준비 결과를 확인한 관리자 적용 또는 승인된 준비 후 전환
  -> 이후 새 인스턴스는 새 release 사용
  -> 기존 인스턴스는 기존 release 사용
```

준비 후 자동 전환은 Backend [PR #178](https://github.com/MSG-CTF/msg-backend/pull/178)의
별도 선택 기능입니다. 이 문서만으로 해당 PR이 병합·배포되거나 운영 설정이 켜지지
않습니다. 원래 생성 경로의 미준비·관측 만료 시 pull fallback과, 이번 **자동 전환에
요구하는 준비 확인**은 서로 다른 조건입니다. 실제 실행의 승인·인증·격리는 계속 필수입니다.

여기서 무중단은 기존 인스턴스를 강제 종료하지 않는 버전 전환을 뜻합니다.
이미 실행 중인 프로세스나 TCP 세션까지 새 이미지로 교체하는 기능은 아닙니다.

## K3s 선언 전환

`misc-reqr`, `pwn-ghost-file`, `pwn-random6`도 K3s 운영 대상으로 전환합니다.
문제 저장소의 `info.yaml`을 `KUBERNETES`로 변경한 뒤 새 발행본을 등록해야 합니다.
과거 `DOCKER` bundle을 수정하거나 runtime_type 검사만 우회해 목록에 포함하지 않습니다.

PWN 문제는 `PWN` 격리 구분을 유지합니다. 선언 변경과 목록 생성만으로 PWN 실행을
승인하지 않습니다. FLAG, 실행 UID, 쓰기 경로, 시작 스크립트와 격리 조건은 문제별
Runtime 정책에서 확인해야 하며, CI가 임의로 root 실행이나 권한 완화를 추가하지 않습니다.

## 현재 확인 범위와 남은 연결

- DevSecOps의 전체 컨테이너 목록 생성·취합 caller는 병합됐습니다. 이는 운영 DB의 active 대조나 실제 전체 다운로드 완료를 뜻하지 않습니다.
- Runtime의 단일 WEB 시범에서는 실제 pull·Pod Ready·imageID·정리를 확인한 자료가 있습니다. 전체 운영 이미지와 Backend·Scheduler 운영 설정 설치 증거로 확대하지 않습니다.
- 실제 일괄 준비에는 Backend active 선택 결과, Runtime 준비 API 배포·전용 인증·허용 target·용량과 소비자 설정 적용 확인이 필요합니다.
- 새 버전 등록·추가 준비·기존 active 보존·준비 후 적용·기존 인스턴스 보존을 실제 환경에서 이어서 검증합니다.
- 다운로드나 목록 변경을 이유로 노드 캐시와 GHCR 이미지를 자동 삭제하지 않습니다. 실행·롤백·적용 대기 보호 목록을 합쳐 별도 리뷰한 삭제 절차만 사용합니다.

연결 책임과 파일 형식은 [노드 이미지 사전 다운로드 연동](node-image-prefetch.md)을 따릅니다.
